# 对接契约词表（63 词｜六层分组）

> 用法：先按 SKILL.md 的六层模型定位层，再查本节对应章节。
> 每条格式：**en｜zh** + 定义 + 要点 + 避坑（或给 AI 的句式）。
> 中英夹杂最省事：说给 AI 时直接甩 `POST /api/orders`、`401`、`cursor` 这类原词，它理解最准。

## 第1层｜请求层（我怎么把话递过去）

### API｜应用程序接口（Application Programming Interface）
- **定义**：两端约好的「点单窗口」——你按约定递参数，它按约定回结果，中间怎么实现互不管。
- **要点**：对接只谈两件事：我要什么（请求）、你给我什么（响应）；实现细节不进契约。
- **句式**：「按这个 API 契约实现，不要改字段名和结构。」

### Endpoint｜端点（接口地址）
- **定义**：一个能干一件事的地址 = **方法 + 路径**，如 `POST /api/orders`。
- **要点**：同一路径不同方法是不同端点：`GET /api/orders` 查列表，`POST /api/orders` 建单。
- **避坑**：别用「URL」泛指——只说路径不讲方法，等于没说清是查还是建。

### HTTP Method｜请求方法
- **定义**：动词，告诉服务端这次是查、建、改还是删。
- **要点**：① 查询用 GET（不改数据、可缓存、幂等）；② 新建或触发用 POST（非幂等）；③ 整体替换用 PUT（幂等）；④ 局部修改用 PATCH（非幂等）；⑤ 删除用 DELETE（幂等）。
- **口诀**：查走 GET、建走 POST、整套换 PUT、改一处 PATCH、删用 DELETE。

### Path Parameter｜路径参数
- **定义**：写在路径里的定位片段，如 `/api/orders/{id}`。
- **要点**：只用于唯一定位一个资源；服务端必须校验归属，防止越权查别人的数据。
- **避坑**：筛选条件、分页参数不要塞进路径——那是查询参数的活。

### Query Parameter｜查询参数
- **定义**：问号后面的 `key=value`，管筛选、分页、排序、关键字。
- **要点**：常见组合 `page` / `pageSize` / `sortBy` / `sortOrder` / `keyword` / `status`。
- **避坑**：GET 理论上能带请求体，但很多网关、代理、缓存会丢弃它——一律用查询参数。

### Request Header｜请求头
- **定义**：随请求走的元信息，不是业务数据。
- **要点**：`Authorization`（带令牌）、`Content-Type`（声明格式）、`Accept`（期望返回格式）、`traceparent`（链路追踪）、`Idempotency-Key`（幂等键）。

### Content-Type｜内容类型
- **定义**：声明请求体的格式，服务端据此挑解析器。
- **要点**：JSON 用 `application/json`；普通表单用 `application/x-www-form-urlencoded`；带文件用 `multipart/form-data`。
- **避坑**：POST 忘写 Content-Type，ASP.NET Core 常直接回 `415 Unsupported Media Type`。

### Request Body｜请求体
- **定义**：真正要提交的数据本体，通常是 JSON 对象。
- **要点**：只放数据，不放页面状态；新建和更新用两套契约（见「空值语义」）。

### Payload｜载荷
- **定义**：一次请求或响应里承载的业务数据本体（去掉头部和包装层的部分）。
- **要点**：说「响应体里的 payload」比说「返回的数据」更准确，AI 不会把包装层也算进去。

### Idempotency｜幂等
- **定义**：同一个请求发 N 次，效果应与发 1 次相同。
- **要点**：GET/PUT/DELETE 天生幂等；POST 靠**幂等键**实现——客户端生成一个唯一键放 `Idempotency-Key` 头，服务端按键去重。
- **场景**：网络抖动重试、用户连点两次提交、会议现场网络不稳后的补发。

### Timeout｜超时
- **定义**：等待响应的上限。
- **要点**：超时**不等于**服务端没处理成功——请求可能已经在写库了。
- **避坑**：超时后能不能重试，取决于这个接口是否幂等，不能一律重发。

### Retry & Backoff｜重试与退避
- **定义**：失败后隔一会儿再试，间隔逐次拉长（指数退避）。
- **要点**：只重试「可重试」错误：超时、`502`/`503`/`504`、`429`；`4xx` 业务错误重试无意义。
- **避坑**：不带退避的密集重试会把服务端在故障时彻底压垮。

## 第2层｜响应层（回来的东西怎么读）

### Status Code｜状态码
- **定义**：三位数字，服务端对这次请求的「结论标签」，比任何文字消息都先被程序读到。
- **要点**：程序只看数字，用户看文案；两者要分开设计。

### 状态码五族
- **1xx 信息**：请求已收到，继续处理（对接基本用不到）。
- **2xx 成功**：`200 OK` 通用成功；`201 Created` 创建成功（建议带回新资源地址）；`204 No Content` 成功但无返回体。
- **3xx 重定向**：`301` 永久、`302` 临时、`304 Not Modified` 协商缓存命中。
- **4xx 客户端错**：`400` 参数格式错；`401` 未认证；`403` 已认证但无权限；`404` 不存在；`405` 方法不对；`409` 冲突（如重复单号）；`415` 格式不支持；`422` 语义校验失败；`429` 请求过多（限流）。
- **5xx 服务端错**：`500` 代码异常；`502` 网关收到非法响应；`503` 服务暂不可用；`504` 网关超时。
- **避坑**：`400` 与 `422` 的边界最容易吵——前者是「格式都不对，根本没法解析」，后者是「格式对，但业务语义不通过」。

### Response Body｜响应体
- **定义**：服务端返回的数据本体。
- **要点**：成功与失败应共用同一外层结构，前端只需写一套解析逻辑。

### Envelope｜统一返回包装
- **定义**：在真正的业务数据外面套一层统一格式，如 `{ code, message, data }`。
- **要点**：包装层放「结论」，`data` 放「内容」；分页结构也放包装层，别塞进 `data` 内部。
- **避坑**：用包装不等于把所有失败都返 200——HTTP 状态码仍要如实反映（见 SKILL.md 坑 1）。

### Business Error Code｜业务错误码
- **定义**：包装层里的 `code`，说明「业务上具体为什么失败」。
- **要点**：建议分段：`0` 成功；`1xxx` 参数与格式；`2xxx` 认证与权限；`3xxx` 业务规则（库存不足、状态不允许）；`9xxx` 系统内部。
- **避坑**：错误码只增不改不删——改了前端的历史分支就全错位。

### Field Naming Convention｜字段命名风格
- **定义**：字段名的拼写约定，常见驼峰 `orderNo`、蛇形 `order_no`、大写 `OrderNo`。
- **要点**：全局统一一种；JSON 字段名**大小写敏感**，`orderNo` 和 `OrderNo` 是两个字段。
- **避坑**：.NET 侧 `OrderNo` 经 System.Text.Json 默认转成 `orderNo`，契约里写明以哪一侧为准，否则前后端各写各的。

### Serialization｜序列化
- **定义**：对象与字符串互转——出站把对象写成 JSON，入站把 JSON 读回对象。
- **要点**：循环引用、枚举、日期、小数精度都是序列化配置问题，不是业务问题。
- **避坑**：同一份契约在不同框架下序列化结果可能不同，验收要拿真实 JSON 比对，而不是看模型类。

### Null Semantics｜空值语义
- **定义**：`null`、空字符串、空数组、字段不存在，这四件事在业务上含义不同。
- **要点**：约定清楚：列表无数据返 `[]` 而不是 `null`；单值无数据返 `null`；更新接口里「字段缺席 = 不改」、「显式 `null` = 清空」。
- **避坑**：不约定就会出现「只想改备注，结果把手机号清空了」。

### Large Integer Precision｜大整数精度
- **定义**：JSON 数字底层是双精度浮点，能精确表示的上限是 `9007199254740991`（2⁵³−1）。
- **要点**：雪花 ID、时间戳拼接 ID、银行流水号超过这个数就会丢精度，一律**以字符串返回**。
- **避坑**：后端返数字、前端收字符串这类「类型漂移」要在契约里一眼看到。

### Timestamp Format｜时间格式
- **定义**：时间怎么写成字符串。
- **要点**：用带时区的标准格式（ISO 8601），如 `2026-10-26T22:00:00+08:00`；并写明是本地时间还是 UTC。
- **避坑**：只写 `2026-10-26 22:00:00` 不带时区，跨端跨库一比就错 8 小时。

### Enum Contract｜枚举契约
- **定义**：有限取值字段（状态、类型）在契约里怎么表达。
- **要点**：优先用字符串枚举（`"Paid"` / `"paid"`），并给出全映射表；用数字必须附对照表。
- **避坑**：直出 `status: 3` 前端只能猜；.NET 要配 `JsonStringEnumConverter` 才输出名称。

### Pagination｜分页
- **定义**：把大列表切成多页取。
- **要点**：① 偏移分页 `page` / `pageSize`（或 `offset` / `limit`）——实现简单，但深页慢、数据变动会重复或漏项；② 游标分页 `cursor` / `nextCursor`——按上一页最后一条往下取，稳定、快，但拿不到总页数。
- **选型判据**：后台管理、页数不多 → 偏移分页；信息流、数据量大、要稳定翻页 → 游标分页。

### Total Count｜总数
- **定义**：符合条件的总条数，用于算总页数、显示「共 N 条」。
- **要点**：总数与列表要**同一时刻**取，否则出现「显示 100 条但翻到第 3 页是空」。
- **避坑**：大表 `count(*)` 很贵——要么单独给「是否有下一页」标志，要么用估算值并标明。

### Sorting & Filtering｜排序与筛选参数
- **定义**：列表的排序字段、方向与筛选条件。
- **要点**：排序字段必须**白名单校验**（不能拼进 SQL），方向只用 `asc` / `desc`；筛选默认可清空。

### Cache Negotiation｜协商缓存
- **定义**：服务端给一个版本标识（`ETag`），客户端下次带上（`If-None-Match`），没变就回 `304` 不给内容。
- **要点**：省流量、快；内网、弱网、静态资源多时收益明显。
- **避坑**：接口返回个性化数据时用错缓存策略，会导致用户看到别人的数据。

### Rate Limit｜限流
- **定义**：单位时间内允许的请求次数上限，超了回 `429`。
- **要点**：响应头常带 `Retry-After` 告诉客户端多久后再试；前端要能识别 `429` 并退避，不当成业务错误弹窗。

## 第3层｜鉴权层（凭什么让我进）

### Authentication vs Authorization｜认证 vs 授权
- **定义**：认证（Authentication）= 你是谁；授权（Authorization）= 你能干什么。
- **要点**：先认证再授权，顺序不能反；对应状态码 `401` 和 `403`。
- **避坑**：把「没登录」和「没权限」都弹成「操作失败」，用户永远不知道该找谁。

### Token｜令牌
- **定义**：服务端签发的一串凭证，客户端每次请求带上以证明身份。
- **要点**：只存令牌不存密码；令牌有有效期；退出登录要让令牌失效或本地清除。

### Bearer Token｜持有者令牌
- **定义**：`Authorization: Bearer <token>` 这种带法——谁拿着它，谁就被当成那个身份。
- **要点**：因此必须走 HTTPS；前端不要把它写进日志（日志里的令牌等于泄露）。

### Access Token / Refresh Token｜访问令牌与刷新令牌
- **定义**：访问令牌短命（分钟级），刷新令牌长命（天级），前者过期用后者换新的。
- **要点**：刷新失败（刷新令牌也过期/被撤销）→ 跳登录页，而不是无限重试。
- **避坑**：没有刷新机制时，用户用着用着突然全页面报错，体验极差。

### Session & Cookie｜会话与 Cookie
- **定义**：服务端存会话状态、浏览器存会话标识的传统方式。
- **要点**：跨域带 Cookie 需要同时开「允许携带凭证」并精确指定源；Cookie 要设 `HttpOnly`、`Secure`、`SameSite`。

### 401 vs 403
- **401 Unauthorized｜未认证**：没令牌、令牌过期、令牌无效——去登录。
- **403 Forbidden｜无权限**：身份没问题，但这个角色不能做这件事——提示「无权限」，别跳登录。
- **避坑**：这两个混用会让前端在「该跳登录」和「该提示无权限」之间做错反应。

### RBAC｜基于角色的访问控制（Role-Based Access Control）
- **定义**：把人分角色、给角色配权限，接口层按「角色/权限点」判定。
- **要点**：接口既要校验「能不能访问这个功能」，也要校验「能不能访问这条数据（归属）」。

### Signature & Nonce｜签名与防重放
- **定义**：把参数 + 时间戳 + 随机数（nonce）按约定算法算签名，服务端验签并拒绝重复 nonce。
- **要点**：防篡改、防重放；政务/内网系统常见。
- **避坑**：签名算法与拼接顺序必须写进契约文档，差一个空格就是全签名失败。

### HTTPS / TLS｜传输层安全
- **定义**：加密传输，防止链路被窃听篡改。
- **要点**：令牌、密码、身份证号这类字段，明文 HTTP 一律不可接受；内网也不例外。

## 第4层｜跨域与环境层（为什么本地能跑线上白屏）

### Origin｜源
- **定义**：`协议 + 域名 + 端口` 三件套，三者任一不同就是不同的源。
- **要点**：`http://a.com` 与 `https://a.com` 是两个源；`localhost:5173` 与 `localhost:8080` 也是两个源。

### Same-Origin Policy｜同源策略
- **定义**：浏览器默认不许 A 源的脚本随意读取 B 源的响应。
- **要点**：这是浏览器的保护，不是服务端的限制——所以 Postman 能通、浏览器不通，是正常现象。

### CORS｜跨源资源共享（Cross-Origin Resource Sharing）
- **定义**：服务端用响应头告诉浏览器「我允许某个源来读我」。
- **要点**：核心是 `Access-Control-Allow-Origin`；还要配 `Allow-Methods`、`Allow-Headers`。
- **避坑**：「本地能跑、线上白屏」八成是这里：线上域名没在允许列表里。

### Preflight｜预检请求
- **定义**：浏览器在发真正的请求前，先发一个 `OPTIONS` 问「我能不能这么发」。
- **要点**：非简单请求才预检——用了 PUT/PATCH/DELETE、带自定义头（如 `Authorization`）、或 Content-Type 不是表单三兄弟。
- **避坑**：预检必须被服务端正确应答，否则真请求根本不会发出去；很多网关默认不放行 `OPTIONS`。

### Credentials 跨域｜携带凭证的跨域
- **定义**：请求要带 Cookie 或授权头时，需要额外允许。
- **要点**：`Access-Control-Allow-Credentials: true`，且 `Allow-Origin` **必须回显具体源**，不能用 `*`。
- **避坑**：通配符 + 凭证 = 浏览器直接拦截，且报错信息很绕，容易查很久。

### Reverse Proxy｜反向代理
- **定义**：外部请求先到代理（Nginx / IIS / 网关），再由它转给真正的应用。
- **要点**：静态页面与接口常由同一个代理分发：`/` 给页面，`/api` 给后端——**同源**，从而根本不需要跨域。
- **避坑**：代理层会改头、加超时；`502`/`504` 基本都是这一层报的，不是你的业务代码。

### Base URL & Environment｜环境基址
- **定义**：接口地址的前缀，按环境不同而不同（本地、测试、生产）。
- **要点**：用相对路径 `/api/...` + 环境基址，别在代码里写死 IP；会议现场换网络时不至于全废。
- **避坑**：把测试环境地址带进生产包，是最常见的上线事故之一。

### Static Assets & CDN｜静态资源与内容分发网络
- **定义**：图片、脚本、样式这些不改的文件，以及分发它们的缓存节点。
- **要点**：静态资源用版本号或哈希命名破缓存；页面入口别做长缓存，否则用户永远看到旧版。

## 第5层｜界面态与交互一致性（用户看到什么）

### Loading State｜加载态
- **定义**：请求进行中的界面表现：转圈、按钮置灰、进度条。
- **要点**：任何超过 200 毫秒的操作都要有；提交类必须禁用按钮，防连点。
- **避坑**：没有加载态 = 用户以为没点上 = 再点一次 = 重复数据。

### Skeleton｜骨架屏
- **定义**：按内容形状先摆灰色占位块，数据到了再填。
- **要点**：首屏、列表、卡片区用它比转圈更稳（不跳动）；局部刷新用局部转圈即可。

### Error State｜错误态
- **定义**：请求失败时界面给什么、能做什么。
- **要点**：① 说人话（「网络不通，请检查连接」）；② 给动作（重试按钮）；③ 保留用户已填内容。
- **避坑**：把后端异常消息原样弹出，用户看不懂还泄露内部信息。

### Empty State｜空态
- **定义**：请求成功但没数据时的界面。
- **要点**：区分「还没有数据」与「筛选后没有结果」——前者引导创建，后者引导清空条件。
- **避坑**：空数组直接渲染成空白表格，用户以为页面坏了。

### Forbidden State｜无权限态
- **定义**：接口返 `403` 时的界面。
- **要点**：明确说「无权限」并给联系方式或申请入口；**不要**静默隐藏或跳登录。

### Optimistic Update｜乐观更新
- **定义**：先按「肯定成功」改界面，失败再回滚。
- **要点**：只用于失败代价小的操作（点赞、勾选、拖拽排序）；涉及钱、库存、审批一律等真实响应。
- **避坑**：乐观更新 + 无回滚 = 用户以为成功了，实际没落库。

### Debounce / Throttle｜防抖与节流
- **定义**：防抖 = 停手后才执行一次（搜索输入）；节流 = 固定间隔最多执行一次（滚动、拖拽、滚动加载）。
- **要点**：搜索框用防抖 300 毫秒左右；列表下拉加载用节流。

### Duplicate Submit Guard｜防重复提交
- **定义**：保证同一业务只提交一次的三道防线。
- **要点**：① 前端按钮禁用；② 请求带幂等键；③ 服务端按键去重。三层都要，缺一层就有漏洞（刷新页面绕过前端、重放绕过网络）。

### Polling / WebSocket｜轮询与长连接
- **定义**：轮询 = 定时问一次「有新的吗」；长连接 = 一条通道双向推。
- **要点**：低频、允许延迟 → 轮询；需要秒级、多端同步 → 长连接；介于两者可用长轮询。
- **避坑**：多端同时改同一单据时，只靠轮询会出现覆盖写——要加版本号或时间戳做冲突检测。

### Offline Degradation｜断网降级
- **定义**：网络不可用时的兜底行为。
- **要点**：至少做到：提示离线、保留待提交内容、恢复后补发（配合幂等）。

## 第6层｜联调治理层（接口变了怎么不炸）

### Contract-First｜契约先行
- **定义**：先定接口契约，前后端各自照契约开发，不互相等。
- **要点**：契约变更要走评审与版本，不能一方悄悄改字段。

### OpenAPI / Swagger｜接口描述规范
- **定义**：用机器可读的格式描述所有端点、参数、响应（OpenAPI 规范，Swagger 是它的工具生态）。
- **要点**：.NET 侧可用内置 OpenAPI 生成；这份文档同时能给 AI 当上下文，让它按真实契约写代码。

### Mock｜模拟数据
- **定义**：按契约造的假响应，让前端不依赖后端进度就能开发。
- **要点**：Mock 必须由契约生成、与契约同步；手写 Mock 迟早与真实接口分叉。

### Environment Isolation｜环境隔离
- **定义**：本地、测试、预发、生产各一套数据与地址，互不污染。
- **要点**：测试数据不要进生产库；生产排查用只读账号。

### Versioning｜接口版本
- **定义**：路径里带版本（`/api/v1/orders`）或头部带版本。
- **要点**：只在不兼容变更时才升版本；版本要能并行存活一段时间。

### Breaking Change｜破坏性变更
- **定义**：会让现有调用方出错的改动：删字段、改字段名、改类型、改语义、把可选变必填。
- **要点**：兼容做法：加字段不加约束、旧字段保留并标记废弃、新字段并行一段时间。
- **避坑**：把「字段从数字改字符串」当小改动，是所有老客户端集体报错的经典事故。

### Trace ID｜链路追踪标识
- **定义**：一次请求从网关到数据库贯穿的唯一标识，日志里都带上它。
- **要点**：用标准头 `traceparent` 传递；前端报错提示里带出来，用户报障时能秒查日志。
- **避坑**：没有它，用户说「刚才提交失败了」，你只能靠时间戳在一堆日志里翻。

### 联调三件套
- **定义**：一次对接必须交付的三样东西：**请求样例、响应样例、错误码表**。
- **要点**：三样齐了，前端不用猜，AI 也不用猜；缺一样就必然来回问。
