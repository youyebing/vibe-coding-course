# 前后端对接契约词汇（第 11 层）

把一次前后端对接拆成 6 层词汇，每层给出能直接说给 AI、也能直接写给同事的词，配契约模板与验收清单。
定位：`frontend-ai-design` 的第 1–10 层回答「页面长什么样」，本技能回答「页面怎么接上你自己的后端」。
不涉及：React/Vue 具体写法、UI 视觉设计（前者直接写代码，后者回 `frontend-ai-design`）。

## When to Use

- 要跟 AI 或前端同事描述「这个接口前端怎么调、失败要怎么显」
- 写接口文档、定错误码、定分页参数、定字段命名风格
- 联调出问题：本地能跑上线白屏、401 和 403 分不清、点了没反馈、重复提交产生两条单
- 给 `frontend-ai-design` 产出的页面补上「接后端」这半边
- **不要用于**：纯 UI 排版与配色（用 `frontend-ai-design`）、纯后端业务实现（直接写代码）

## 核心方法：对接六层模型

| # | 层 | 问自己 | 代表词（全表见 references/contract-glossary.md） |
|---|---|---|---|
| 1 | **请求层** | 我怎么把话递过去？ | Endpoint、请求方法、路径参数、查询参数、请求头、Content-Type、请求体、幂等 |
| 2 | **响应层** | 回来的东西怎么读？ | 状态码五族、响应体、统一包装、业务错误码、字段命名、空值语义、时间格式、分页 |
| 3 | **鉴权层** | 凭什么让我进？ | 认证 vs 授权、令牌、Access/Refresh、401 vs 403、角色权限、签名防重放 |
| 4 | **跨域与环境层** | 为什么本地能跑线上白屏？ | 源、同源策略、跨源资源共享（CORS）、预检请求、反向代理、环境地址 |
| 5 | **界面态层** | 用户看到什么？ | 加载态、骨架屏、错误态、空态、无权限态、防抖节流、防重复提交 |
| 6 | **联调治理层** | 接口变了怎么不炸？ | 契约先行、接口描述规范（OpenAPI）、模拟数据、版本号、破坏性变更、链路追踪标识 |

> 记忆锚：**前两层管「说清楚」，中间两层管「进得去」，后两层管「看得见、改得动」。**
> 排错锚：联调任何怪现象，先问它掉在哪一层——4xx 是前三层，白屏先查第四层，没反馈查第五层，改了接口才坏的是第六层。

## 一次对接的流程（五步）

1. **定契约**：把端点清单写成表（端点、方法、路径、请求字段、响应字段、错误码），见 `references/contract-templates.md` 模板 A。
   *判据*：另一个没参与讨论的人能只凭这张表写出调用代码，且不需要反问。
2. **定状态码与业务码的分工**：HTTP 状态码管「传输与语义」（成功/参数错/没权限/服务端挂），业务错误码管「具体为什么」。两层都要有，不许只用 200。
   *判据*：一份错误码表里，每个业务码都挂在一个明确的 HTTP 状态码族下。
3. **定界面四态与交互**：加载、错误、空、无权限，每种都有明确呈现；提交类操作必须防重复。
   *判据*：断网、500、空列表、越权四种情况各说得出用户看到什么。
4. **定跨域与环境**：本地/测试/生产三套地址、允许的源、是否带凭证、鉴权头怎么带。
   *判据*：新环境部署后，浏览器控制台零跨域报错，且不再出现「本地能跑线上白屏」。
5. **联调验收**：照 `references/contract-templates.md` 模板 E 逐条打勾，不靠「看着好像对了」。
   *判据*：清单每一项都有实测记录（截图或请求样例），没有「应该没问题」。

## 验收清单（AI 或人交付后逐条打勾）

- [ ] 每个接口写清了方法 + 路径 + 请求字段 + 响应字段 + 可能的错误码
- [ ] 成功、参数错误、未登录、无权限、服务端错误各自的 HTTP 状态码明确且不混用
- [ ] 业务错误码有分段规则（如 1xxx 参数、2xxx 权限、3xxx 业务规则），前端能按段兜底
- [ ] 字段命名风格全局统一，并写明是否大小写敏感
- [ ] 长整型 ID 以字符串返回，不出现精度丢失
- [ ] 时间为带时区的标准格式，并写明是本地时间还是 UTC
- [ ] 列表接口有分页参数与总数（或明确说明用游标分页、无总数）
- [ ] 未传 / 传空 / 传 null 三种语义在更新接口上有明确约定
- [ ] 前端有加载态、错误态、空态、无权限态四种呈现
- [ ] 提交按钮在请求期间禁用，重试走幂等键而非裸重发
- [ ] 跨域配置在真实域名下验证过，带凭证时未使用通配符
- [ ] 错误提示不把堆栈或内部表名暴露给用户
- [ ] 接口文档与实际返回一致（用真实请求抽查 1 个接口）

## Pitfalls

1. **以为「成功就是 200、失败就是业务码」**——这是最常见的地基错误。网关超时返 504、鉴权失败返 401，这两种根本不会走进你的业务码分支，前端会把它当「未知错误」吞掉。
2. **.NET 序列化默认把字段名转驼峰**：ASP.NET Core 的 System.Text.Json 默认 camelCase，后端 DTO 写 `OrderNo`，前端收到的是 `orderNo`。契约里必须写明按哪一侧为准，否则字段名对不上。
3. **长整型主键丢精度**：JSON 数字走双精度浮点，超过 `9007199254740991`（2⁵³−1）会被四舍五入。雪花 ID、时间戳拼接 ID 一律以字符串传。
4. **更新接口分不清「没传」和「传 null」**：不约定就会「只想改备注，结果把手机号清空了」。
5. **跨域带凭证还用通配符**：允许携带 Cookie/授权头时，`Access-Control-Allow-Origin` 不能写 `*`，必须回显具体源并允许凭证，否则浏览器照样拦。
6. **重试不幂等**：超时后重发，用户看到「提交失败」又点了一次，服务端落两条。重试与防重复提交是同一件事的两面。
7. **枚举直出数字**：`status: 3` 前端只能猜；要么字符串枚举，要么在契约里给全映射表。
8. **错误提示直接透传后端异常消息**：既是信息泄露，也让用户看不懂。面向用户的文案与面向前端的错误码要分开。

## Verification

- 想查词：`references/contract-glossary.md` 按六层分组，每条含定义、要点、避坑、给 AI 的句式。
- 想要模板：`references/contract-templates.md` 有契约表、响应包装样板、错误码分段、提词模板、联调清单。
- 判定通过：拿一个你自己的真实接口，按上面验收清单跑一遍——能全部打勾才算这套词学会了；打不了勾的项，就是这次要跟 AI 说的那句话。
