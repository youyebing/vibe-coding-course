# Socratic Requirement Clarification Skill

苏格拉底式需求澄清流程：一次一问把需求挖透，全量复述确认后才开工。只负责把需求本身问清楚，不产出实施方案。纯流程 skill，无工具或环境依赖。

## When to Use

> 定位：本 skill 是**工程需求澄清**——锁定交付物（范围、默认处理、开工自检）。若用户连自己想问什么都说不清、认知混乱（「我不知道该问什么」「我到底该怎么办」），先转 `socratic-inquiry`（通用苏格拉底问诊，重建问题本身）再回来对交付物。

- 用户给出模糊需求就动手 = 返工：「帮我改进这个」「优化一下」「我想要 X 但说不清」
- 用户明确要求「先提问直到完全理解」
- 猜错代价高：改动范围大、规则相互牵连、交付后难回退

Don't use for:

- 需求明确无歧义、输入输出清晰的单点修改——直接执行
- 猜错代价很小——直接替用户拍板并明说（见 Procedure 第 2 步）
- 紧急的一次性操作（查个日志、跑个命令）——不值得提问轮次

## Procedure

1. **先读完材料再提问。**用户给了 URL/仓库/文件，先用 `read_file` / `web_extract` 完整读一遍——很多问题的答案和真正的矛盾点都藏在材料里。带着读过的上下文提问，不许裸问。完成标准：能指出材料里相关答案与疑点的位置。**用户什么材料都没给时，先引导说出三样：背景（这件事处在什么处境里）、痛点（哪个瞬间/哪次经历觉得不对劲）、需求（期望的产物长什么样）**——三者不必一次问全，按序一次一问，痛点优先从具体经历切入。
2. **一次只问一个问题。**问到认为完全理解为止，问题数量不设上限，但不许为问而问。完成标准：每个待问的问题都能写出「这个答案会改变什么」。
3. **选项化提问。**能给选项就 A/B/C 选项 + 你的推荐（「我推荐 A，因为…」），让用户选而不是从零组织语言；真开放的问题才留白。
4. **从具体经历问起。**「回忆最近一次……哪个瞬间觉得不对劲」比「你的痛点是什么」挖得深——用户常说不清抽象痛点，但讲得出具体事故。
5. **用户纠正你时，复述修正后的理解请他确认。**（例：你以为时序图画 agent 协作，用户说画的是程序自身功能——立刻复述「我理解对了吗：图描述程序自身的功能，不是任务执行过程」，确认后再继续。）完成标准：用户明确确认。
6. **答案与既有规则冲突时当场摆出来。**（例：用户说上限可以放大，但原规则里有一整套逻辑挂在旧上限上——列出来问怎么改，别默默改。）
7. **每个决定编号记账。**问题按序编号（第一问、第二问……），每条答案记下「选了什么 + 为什么」。
8. **理解合拢后全量复述。**按逻辑链（不按提问顺序）整理所有决定成表格/清单，列出改动范围和默认处理方式，问「有没有走样、遗漏、想反悔的」。完成标准：用户确认「没走样」。
9. **开工后对照决定逐条落实，交付时自检一致性。**（如：术语统一、新旧规则无残留冲突。）完成标准：决定清单里每一条都能在交付物中核对到。

## Pitfalls

- 打包多问（一轮 5 个）：用户挑着答、误解埋得深，纠错成本高。一次一问的代价是轮次多，但每轮便宜。
- 用户答「都可以/你定」：给一个默认值并明说「我替你定了 X，理由 Y」，不许悬空。
- 把复述写成计划书：复述的是「我对需求的理解」，不是「我的实施方案」——用户要核对的是前者。
- 用户中途改主意：正常，更新决定清单，受影响的已做部分主动指出。
- 问太多废问题消磨耐心：每问一句「这个答案会改变产物吗」，不会就闭嘴替领导拍板。

## Verification

- 复述清单里每条决定都能回溯到用户某句话。
- 开工后自检清单覆盖全部决定。
- 用户确认「没走样」才动手。
