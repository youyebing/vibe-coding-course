# Socratic Inquiry Skill（通用苏格拉底问诊）

一次一问帮用户找到**真正值得回答的问题**：人类经常嘴上问的和心里真正想表达的不是一个意思。先完成认知重建（reframe），确认新问题后才给判断和行动。

> 来源：提炼自数字生命卡兹克《都Agent时代了，我还是想分享给你这12个我最常用的Prompt》(2026-08) #1 苏格拉底式提问；触发框架参考同作者《从0开始，12步学会用好AI》第6步（【背景、痛点、需求】+ "先不要开始干活，先向我提问"）。

**与近亲 skill 的分工**：
- `socratic-requirement-clarification` = 工程需求澄清，目标是**锁定交付物**（范围、默认处理、开工自检），面向"模糊需求就动手会返工"。
- 本 skill = 通用认知问诊，目标是**重建问题本身**（用户说不清自己想问什么、纠结、想法互相打架），不产出实施方案。
- 双向互链：问诊中用户表现出一旦问题理清就要立刻去干活/要交付物 → 转 `socratic-requirement-clarification`；需求澄清中发现用户其实连问题都没想清 → 转本 skill。

## When to Use

- 用户明显困惑、纠结、说不清：「我不知道该问什么」「我到底该怎么办」「帮我理理思路」
- 用户给了任务但默认前提太多、目标模糊，动手前需要先校准问题（先问诊，别急着做）
- 用户主动要求「先不要开始干活，用苏格拉底提问法向我提问，一次只问一个问题，直到完全理解」
- 用户描述里混着事实、猜测、情绪和期望，需要先分层

Don't use for:

- 需求明确无歧义、要交付物的工程任务 → `socratic-requirement-clarification` 或直接执行
- 已有候选答案、纠结二选一 → `steelman-bidirectional`（双向钢人论证）
- 用户只要信息/答案，不要问诊（查资料、算数、打听事实）→ 直接回答
- 紧急一次性操作 → 不值得提问轮次

## Procedure

1. **先读完材料再提问。** 用户给了 URL/仓库/文件，先用 `read_file` / `web_extract`（或浏览器）完整读一遍——真正的矛盾点往往藏在材料里。完成标准：能指出材料里相关答案与疑点的位置，不许裸问。
2. **一次只问一个问题，最多 6 个。** 根据用户的回答决定下一问，绝不提前掏一整套问卷。用普通对话发问即可（保持一问一条消息）。
3. **听回答时做四分类**：这是可验证的事实、对事实的解释、价值判断，还是希望实现的目标？优先补齐缺失的类别——大多数混乱来自把价值判断当事实说。
4. **逐项检查**：关键词是否含糊（"更好/优化/合理"指什么）？默认了哪些前提？证据来自哪里？有没有相反解释？结论成立或不成立分别意味着什么？
5. **每问之前，用一句话说明上一条回答让你更新了什么判断。** 让用户看到你在跟他的思路走，而不是背问卷。
6. **只问可能改变结论的问题。信息足够时立刻停止，不凑满 6 个。** 这个 Skill 的及格线是"问完不烦人"。
7. 问诊结束后整理出 **六要素**：
   1. 最开始问的问题；
   2. 真正想解决的问题；
   3. 已经确认的事实；
   4. 仍未验证的假设；
   5. 最可能改变结论的关键变量；
   6. 一个准确、具体、可以继续行动的新问题。
8. **等用户确认这个新问题以后**，才给出判断、理由和下一步行动。未确认前不给方案。

## Pitfalls

- 打包多问（一轮 5 个）：用户挑着答、误解埋得深。一次一问的代价是轮次多，但每轮便宜。
- 凑满 6 个：信息够了还在问 = 拷打。作者自己都抱怨过 grill me 类工具"无限追问导致我很烦"。
- 过早给建议：还没确认新问题就输出方案，用户会顺着你的框架走，反而丢了真问题。
- 把价值判断当事实接受：用户说"我觉得 X 不行"时，先问"这是事实还是感受/推断"再决定要不要深挖。
- 用户答「都可以/你定」：给一个默认值并明说「我替你定了 X，理由 Y」，不许悬空。
- 分不清认知问诊和需求澄清：用户要的是交付物就转 `socratic-requirement-clarification`，不然会问一堆不指向交付的问题。

## Verification

- 六要素中的「真正想解决的问题」和「新问题」得到用户明确确认。
- 未确认前没有给出任何判断/建议。
- 每一条「更新了什么判断」能回溯到用户说的某句话。
- 提问数 ≤ 6，且停止得早于用户不耐烦（用户没说"别问了"）。
